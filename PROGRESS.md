### The honest caveat

`TACHI_PROVIDER=fixture` is not a network. It is an in-process ledger that runs the *same*
adapter code path — same transaction construction, same signing, same id derivation, same
broadcast/ack handling — against a deliberately faithful stand-in for the daemon (including
CometBFT's habit of returning HTTP 200 with a failure `code` inside the body, and the
`nonce`/duplicate-vtxo rejection rules). It exists so the whole application is testable in CI and
so reviewers can click through the flow without provisioning a chain.

**It is never allowed to claim to be live.** The provider is reported in every response envelope
(`mode: "fixture"`), the header shows a FIXTURE badge, and `mode: "live"` is only ever emitted by
`LiveTachiDaemon`. The `!` screenshot-level claim — a real invoice paid by a real VTXO with a real
explorer link — has to be made on a live daemon, and the Day-1 gate is what decides whether it can
be made.

## Build log

### Day 1 — the gate (`scripts/spike-tachi.ts`)

The gate probes each capability the merchant loop depends on and prints a truth table with a
remediation for every red row. Capabilities are graded `critical` (the merchant loop cannot work
without it), `important` (a demo path degrades), or `optional`.

It exists because "it works on my machine" is not a claim anyone can check. Running it produces a
receipt; running it with `--write` also writes `docs/spike-latest.json`, and a red critical row
makes the process exit non-zero, so the same command can gate a deploy.

### Day 2 — the adapter and the merchant loop

- `LiveTachiDaemon` speaks the real daemon: `status`, `validators`, `getbalances`, `listvtxos`,
  `gettx`, `faucet`, and `broadcastTxSync` with CheckTx interpretation.
- `TachiRail` owns value movement: onboard (faucet → account → VTXO), transfer with greedy
  largest-first coin selection, withdrawal to a P2TR address, and the signing envelope
  (`buildVtxoPsbt` → `signVtxoPsbtAsUser` → `buildTachiTx*` → `signTachiTx`).
- Typed errors throughout (`DaemonUnreachable`, `ProofStale`, `InsufficientCapacity`,
  `RouteUnavailable`, `AdapterError`) so the API can answer 402/409/503 honestly rather than 500.
- The API grew the merchant lifecycle: quote → select → settle (with fallback), detection polling,
  refunds, payouts, webhooks, dashboard summary, and a public pay-page endpoint that exposes only
  what a customer needs.

### Day 3 — the bugs the click-path found

Writing the click-path as a script instead of clicking it by hand paid for itself immediately. Two
defects would have shipped, and one of them would have been the worst possible bug for this product:

- **A false confirmation.** A merchant payout of 1,000 sats left ~499,000 sats of change at the
  merchant's own vault address. Detection asked "is there a new VTXO at the payment target at least
  as large as the invoice?" — yes — and marked a pending invoice **paid**. A real merchant would
  have shipped goods for money that never arrived. Fixed by: only counting outputs the merchant did
  not create for itself (`selfOwnedVtxoIds` on every spend), preferring an exact-amount match,
  requiring a real VTXO baseline at invoice creation, and refusing to credit one ledger output to
  two invoices at once. Regression tests fail without the fix — verified by reverting it.

  The root cause is a design tradeoff worth naming: every invoice shares one payment target, so
  attribution is inference rather than identity. Deriving a fresh address per invoice is the real
  fix and is listed as next work; the current rules are the honest version of what one shared
  address can support.
- **A status pill that lied.** Every 4xx was stamped `mode: "degraded"`. A merchant who mistyped a
  sweep destination would watch the daemon indicator turn amber and conclude the network was down.
  The pill now reports the daemon's actual state on failures too.

## Known gaps

1. **The live gate is unrun here.** This checkout was developed in a sandbox without TLS access to
   `*.tachibtc.com`, so the live capabilities in the table above are unverified by construction.
   Every one of them is probed by `npm run spike:tachi`; the video and the submission should only
   cite the rows that this command prints green on the machine of record.
2. **The withdraw path is the least-exercised code.** It requires a P2TR destination, a CSV-aware
   redemption transaction, and a block to confirm. Its unit tests cover construction and refusal;
   the live confirmation is what the gate needs to show.
3. **Attribution is inference, not identity.** All invoices share the merchant's payment target,
   so "new VTXO ≥ amount" is the rule, hardened by the exact-amount preference, the self-spend
   exclusion and the credited-once registry. Per-invoice derived targets remove the ambiguity
   entirely and are the first item of next work.
4. **Webhook retries use in-process backoff.** Correct and visible in the delivery log, but a
   process restart drops the retry queue. A durable queue is the next step, and the delivery log is
   honest about which attempt failed.
5. **Single-merchant policy.** The store is in-memory JSON; multi-tenancy, persistence and
   per-merchant API keys are deliberately out of scope for the hackathon.
